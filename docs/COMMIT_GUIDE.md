# 提交与发版规范

本文档定义了本项目的版本管理、变更记录和 Git 提交流程。**所有代码变更（包括 AI 辅助编写）必须遵循此规范。**

---

## 1. 版本号规则

采用 [语义化版本](https://semver.org/lang/zh-CN/) `MAJOR.MINOR.PATCH`：

| 变更类型 | 版本位 | 示例 | 说明 |
|----------|--------|------|------|
| 新功能 / 大特性 | MINOR | `3.12.0` → `3.13.0` | 新增用户可感知的功能模块 |
| 缺陷修复 / 小优化 | PATCH | `3.13.0` → `3.13.1` | 修 bug、优化逻辑、调整 UI 细节 |
| 破坏性变更 | MAJOR | `3.13.1` → `4.0.0` | 不兼容的数据格式或 API 变更 |

---

## 2. 版本号同步清单

修改版本号时，必须同步更新以下所有位置：

- [ ] `package.json` — `"version"` 字段
- [ ] `package-lock.json` — 顶层 `"version"` 及 `packages[""]` 中的 `"version"`
- [ ] `public/index.html` — 侧边栏徽标 `.sidebar-version` 和首页徽标 `.version-badge`
- [ ] `CHANGELOG.md` — 顶部版本声明和新增条目标题

> **验证**：运行 `node test/test-version.js` 确认所有位置版本一致。

---

## 3. CHANGELOG 格式

### 头部版本声明

```
目前系统版本为 **v{VERSION}** (更新日期: {YYYY-MM-DD})。
```

### 条目格式

新条目插入在头部声明下方、上一版本条目上方：

```markdown
## {EMOJI} v{VERSION} {简要标题} [{TAG}]

- **改动点一**：具体描述，说清楚改了什么、为什么改、用户感知是什么。
- **改动点二**：同上。
```

### 标签与 Emoji 对照

| 标签 | Emoji | 用途 |
|------|-------|------|
| `[NEW]` | ✨ | 新功能 / 新特性 |
| `[FIX]` | 🔧 | 缺陷修复 / 小优化 |
| `[BREAKING]` | 💥 | 破坏性变更 |

---

## 4. Commit Message 格式

```
v{VERSION} {简要标题}

- 改动点一的一句话描述
- 改动点二的一句话描述
- 改动点三的一句话描述
```

**示例**：

```
v3.13.1 自定义标的命名优化

- 单标的组合自动以 ticker 作为名称，无需手动填写
- 前端单标的时名称框自动填充并置灰，多标的恢复可编辑
- 补充单标的命名边界测试及集成测试适配
```

### 规则

- 标题行以 `v{VERSION}` 开头，后接中文简要描述，**不加句号**
- 标题行与正文之间空一行
- 正文用 `- ` 列表，每条一个独立改动点
- 用中文撰写，术语（如 ticker、API）保留英文

---

## 5. 完整提交流程

按以下顺序操作，缺一不可：

```
1. 完成代码改动
2. 运行相关单元测试，确认通过
3. 确定版本号变更类型（PATCH / MINOR / MAJOR）
4. 同步更新版本号（见第 2 节清单）
5. 更新 CHANGELOG.md（见第 3 节格式）
6. 运行 node test/test-version.js 确认版本一致性
7. git add -A && git commit（见第 4 节格式）
```

---

## 6. 注意事项

- **不要跳过版本校验测试**，它会检查 `package.json`、`package-lock.json`、`index.html`、`CHANGELOG.md` 的版本是否一致。
- **CHANGELOG 条目要面向用户**，描述用户可感知的变化，而非纯技术实现细节。
- **一次 commit 对应一个版本号**，不要在同一个版本号下多次 commit 不同功能。
